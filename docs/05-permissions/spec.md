# Sirius-Agent（五层防御权限系统）Spec

## 背景

Sirius-Agent 当前已实现基础 Agent Loop（agent.py）：模型可调用 read_file、write_file、edit_file、execute_command、glob_files、grep_content 六个工具。现有机制里，工具按 `safe` 布尔值分两档——只读工具（read_file/glob_files/grep_content）标记 safe=true，并发执行、不经过任何拦截；有副作用工具（write_file/edit_file/execute_command）标记 safe=false，串行执行，同样不经过任何拦截或确认。文件类工具已有一层基础路径沙箱（tools/paths.py 的 resolve_safe_path），限制读写落在工作目录内，但目前是唯一的安全机制，且不可配置、不可查看命中原因。

本阶段要在此基础上装一套五层防御的权限系统：黑名单硬拦截危险命令、路径沙箱、可配置规则引擎、多档权限模式、人在回路确认。所有工具（含只读工具）都要经过这套系统判定，但只读工具默认更宽松，避免日常读文件被打断。权限被拒绝时不终止 Agent Loop，把结果当作一次失败的工具调用反馈给模型，让模型有机会调整策略（例如换一种方式完成任务，或向用户说明受限原因）。

## 目标

- 在执行任何工具调用前，得到一个明确的 allow/ask/deny 判定，并且判定依据可解释（是哪一层、哪条规则给出的）
- 危险命令、越界文件访问默认不会被无意放行；同时给信任更高的用户留出"整体调宽"和"逐条放行"的空间
- 权限判定不打断 Agent Loop 的可继续性——deny 和用户在人在回路中拒绝，都作为一次工具失败结果反馈给模型，循环继续
- 规则的存放位置（用户级/项目级/本地级）只影响写到哪个文件，不影响判定优先级；所有来源的规则合并成一个集合参与判断

## 功能需求

- F1: execute_command 工具的 command 参数在执行前先过一道正则黑名单，命中已知高危命令类别（如删除系统关键目录、磁盘格式化/写裸设备、远程下载脚本直接执行、fork 炸弹、关机重启系统等）时直接拒绝执行，且这层判断不受规则配置、权限模式、人在回路影响——命中即拒绝
- F2: read_file / write_file / edit_file 三个工具在执行前解析 path 参数得到的真实路径（先解析符号链接，再做前缀判断），判断是否落在工作目录内；glob_files / grep_content 因参数本身不接受任意路径，结构上不做越界判断
- F3: 越界的文件路径访问，只有在存在一条显式匹配的 allow 规则，或当前权限模式为 bypass 时才可以放行；否则一律拒绝，不进入人在回路询问
- F4: 支持以「工具名(模式)」的形式声明规则，例如 `execute_command(git *)` 表示放行所有以 git 开头的命令；模式支持精确字符串匹配和 glob 通配匹配；execute_command 类规则的模式匹配其 command 参数，read_file/write_file/edit_file 类规则的模式匹配其 path 参数
- F5: 每条规则的判定结果是 allow、ask、deny 三选一之一
- F6: 规则分别存放在用户级、项目级、本地级三个 YAML 文件中；读取时把三处规则合并成一个集合参与判断，判定优先级只看结果严重度——deny 压过 ask、ask 压过 allow——与规则写在哪个文件无关；不考虑规则模式的精确度（广泛规则和精确规则同等对待）
- F7: 支持 default、accept_edits、plan、bypass 四档权限模式整体切换；当某次工具调用在合并后的规则集合中找不到任何命中的规则时，按当前模式和该工具所属类别（read/write/command）给出兜底默认判定：
  - read 类工具（read_file/glob_files/grep_content）：四档下都兜底 allow
  - write 类工具（write_file/edit_file）：default 兜底 ask，accept_edits 兜底 allow，plan 兜底 ask，bypass 兜底 allow
  - command 类工具（execute_command）：default、accept_edits、plan 都兜底 ask，bypass 兜底 allow
  - plan 档额外接管"只把只读工具暴露给模型"这件事：处于 plan 档时，模型这一轮能看到的工具列表本身就只有 read 类工具，上面 write/command 类的兜底值是防御性的兜底（万一模型仍尝试调用未暴露的工具）
- F8: 权限模式可以在启动时通过命令行参数指定（默认"默认"档），也可以在会话中用斜杠命令随时切换
- F9: 一次工具调用的最终判定，按以下顺序确定：
  1. execute_command 先过黑名单（F1），命中则 deny，判定结束
  2. 路径类工具做越界判断（F2/F3）；若越界，只能由显式 allow 规则或放行模式判定为 allow，否则 deny，判定结束
  3. 若合并后的规则集合中有命中的规则（F4/F6），按命中规则结果（deny 压过 ask 压过 allow）判定，判定结束
  4. execute_command 若命中安全命令白名单（F14），判定为 allow，判定结束
  5. 都没命中时，按当前权限模式给出兜底默认值（F7）
- F10: 当第 9 条最终判定为 ask 时，中断当前这次工具调用的执行，把工具名、参数、判断依据展示给用户，等待用户选择：允许（仅本次）、拒绝（仅本次）、允许（本会话内不再询问同类调用）、允许（永久写入本地规则文件）
- F11: 用户选择"本会话允许"或"永久允许"时，系统基于本次调用参数生成一条泛化后的 glob 规则（如 execute_command(git *)），展示给用户确认或修改后：本会话选项只存在进程内存中，直到本次会话结束；永久选项额外写入本地级 YAML 规则文件
- F12: 最终判定为 deny（无论来自黑名单、沙箱、规则、模式兜底还是人在回路拒绝）时，该工具不执行，返回一条结构化失败结果反馈给模型，Agent Loop 不因此终止，继续下一轮迭代
- F13: 人在回路的询问在终端中严格串行：一批工具调用中若有多个都需要询问，逐个展示、逐个等待用户输入，不并发弹出多个询问
- F14: execute_command 内置一份硬编码的安全命令白名单（如 ls/cat/git status 等已知无副作用的只读命令），命中且合并规则集合未命中任何规则时直接放行、不走模式兜底；这层优先级低于规则引擎（用户显式配置的规则，包括 deny，永远能覆盖白名单）、高于模式兜底；命令里出现管道/分号/重定向/命令替换等 shell 元字符时一律不算命中白名单，即使基础命令本身在名单里

## 非功能需求

- N1: 权限判定（黑名单正则匹配、沙箱路径解析、规则匹配、模式兜底）是纯本地计算，不发起任何网络请求，判定耗时不应造成用户可感知的额外延迟
- N2: 每一次判定结果都能说清楚依据——是黑名单命中（及命中的类别）、沙箱越界、合并规则集合中的哪一条规则、还是权限模式的兜底默认值；这份依据在人在回路询问用户时、以及工具被拒绝反馈给模型时都要能体现
- N3: 用户级/项目级/本地级规则 YAML 文件缺失时视为空规则集合，不报错；文件存在但格式错误（不是合法 YAML、字段缺失、action 不是 allow/ask/deny 三者之一等）时，启动阶段给出清晰错误提示后退出，而不是抛出未处理异常堆栈或静默忽略
- N4: 黑名单的正则规则需要覆盖项目实际运行的平台（Windows PowerShell/cmd，参见 execute_command 工具已有的 win32 分支），不能只覆盖类 Unix 命令变体
- N5: 代码需要有中文注释（遵循项目 CLAUDE.md 约定）

## 不做的事

- 不做网络请求限制、资源配额（CPU/内存等）、审计日志，留给后续章节
- 不做黑名单的用户自定义/扩展——黑名单条目固定写死在代码里，用户不能新增、删除或修改
- 不做 execute_command 之外工具的黑名单式硬拦截（如 write_file 按文件名黑名单硬拒绝）——硬拦截只针对 execute_command 的 command 参数
- 不做规则文件的交互式管理命令（如 /rules list、/rules remove 等）——除了人在回路自动生成规则这一条路径外，其余规则增删改查都靠用户手动编辑 YAML 文件
- 不做运行中规则文件被外部编辑后的自动热重载；程序只在启动时以及人在回路写入本地规则文件后同步一次内存中的合并规则集合
- 不做拒绝方向的"本会话/永久记住"——人在回路的拒绝只影响本次调用，下次同类调用仍会重新判定
- 不做规则/模式配置的图形化界面，只支持 YAML 文件和命令行/斜杠命令

## 验收标准

- AC1: 模型请求 execute_command 执行黑名单命中的命令（如删除根目录一类的命令）时，命令不会被真正执行，程序直接拒绝并把拒绝原因（命中黑名单及类别）反馈给模型，Agent Loop 继续到下一轮，不会终止
- AC2: 模型请求 read_file/write_file 访问一个解析后（含符号链接被展开）落在工作目录之外的路径，且既没有匹配的显式 allow 规则、当前权限模式也不是 bypass 时，该次调用被直接拒绝，不进入人在回路询问
- AC3: 在权限模式为 bypass 时，同一个越界路径的调用能被允许执行
- AC4: 在权限模式为 default、accept_edits 或 plan 时，只要配置了一条显式匹配该越界路径模式的 allow 规则，该越界调用也能被允许执行
- AC5: 分别在用户级、项目级、本地级三个 YAML 规则文件中，为同一个工具+参数模式各写一条结果不同的规则（如一处 allow、一处 deny），程序合并后按 deny 压过 allow（压过 ask）生效，且调整规则写在哪个文件不影响最终结果
- AC6: 同一次调用同时命中一条广泛的 glob 规则和一条精确规则，且两者判定结果不同时，最终结果按结果严重度（deny>ask>allow）决定，与哪条规则更精确无关
- AC7: 对同一个未命中任何规则的 write 类工具调用（如 write_file），分别切到 default/accept_edits/plan/bypass 四档权限模式，兜底判定依次为 ask/allow/ask/allow；对同一个 command 类工具调用（execute_command），四档依次为 ask/ask/ask/allow
- AC8: 对只读工具（read_file/glob_files/grep_content）的调用，在 default/accept_edits/plan/bypass 四档权限模式下，只要没有命中拒绝性质的规则，都直接放行、不打断对话
- AC17: 权限模式切换到 plan 时，Agent Loop 向模型请求这一轮工具列表时只暴露只读工具，并周期性注入计划模式提醒；切到其他档位后模型能看到全部工具
- AC18: 模型请求 execute_command 执行一条命中安全命令白名单、且没有配置任何规则的命令（如 `ls -la`）时，在 default 模式下直接放行、不弹出人在回路询问
- AC19: 用户为某条命中白名单的命令显式配置一条 deny（或 ask）规则后，该规则优先于白名单生效
- AC20: 命中白名单的基础命令后面拼接了管道/分号/重定向/命令替换等 shell 元字符（如 `ls; rm -rf /`）时，不算命中白名单，按正常流程继续走黑名单/规则/模式兜底判断
- AC9: 用 `--permission-mode` 启动参数指定初始档位生效；会话中用斜杠命令切换档位后，后续判断立即按新档位生效
- AC10: 触发 ask 判定时，终端展示工具名、参数和判断依据，等待用户输入；选择"允许（仅本次）"后该次调用被执行，且不生成任何持久规则——下一次同类调用仍会重新询问
- AC11: 选择"允许（本会话）"时，程序展示泛化后的 glob 规则供确认/修改，确认后该次调用被执行，且本会话内后续同类调用直接放行、不再询问；重启程序后该规则不再生效
- AC12: 选择"允许（永久）"时，确认后的规则被写入本地级 YAML 文件；重启程序重新加载规则后，同类调用依然直接放行
- AC13: 选择"拒绝（仅本次）"时，该次调用被拒绝并反馈给模型，Agent Loop 不终止；下一次同类调用仍会重新询问
- AC14: 一批工具调用中有多个都触发 ask 判定时，程序逐个串行展示、逐个等待用户输入，不会同时出现多个待确认的询问
- AC15: 规则 YAML 文件存在但格式错误（非法 YAML、缺字段、action 不是 allow/ask/deny 之一）时，程序在启动阶段给出清晰错误提示并退出，而非抛出未处理异常堆栈
- AC16: 用户级/项目级/本地级三个规则文件都不存在时，程序正常启动，所有工具调用的判定完全走权限模式兜底逻辑
