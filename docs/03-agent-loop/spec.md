# Sirius-Agent（Agent Loop）Spec

## 背景

Sirius-Agent 第二期（02-tools）已经交付了工具系统：模型能在一轮对话里请求调用一个或多个工具，系统执行后把结果喂回模型，模型基于结果给出这一轮的最终回复——但到此为止，不会自己判断"是否还需要再调用一次工具"。这意味着任何需要多步操作才能完成的任务（先读文件、再据此写文件、再跑命令验证），都得用户在每一步之间手动催促模型继续，模型无法自主完成一个完整任务。

这一期要把"单轮工具往返"升级成真正的 ReAct 循环（想 → 做 → 看结果 → 再想，直到任务完成），并配套完善的停止条件、异步事件流、并发执行策略和 Plan Mode，让 Sirius-Agent 从"能用工具的聊天机器人"变成"能自主完成多步任务的 Agent"。

## 目标

- 把 02-tools 中"最多两次请求"的固定流程，改造成不限次数往返的 ReAct 循环：模型不再请求工具即视为任务完成
- 提供多重停止条件作为安全网，防止循环失控（迭代上限兜底，另有正常结束/用户取消/连续未知工具/流式错误四种主动终止路径）
- 把 Agent 核心逻辑全面迁移到 asyncio，产出一套异步事件流（文本、工具调用、工具结果、Token 用量、进度、终止原因），让 Agent 与终端界面彻底解耦
- 流式响应双路收集：一边实时把文本推给界面展示，一边在内部攒出本轮完整文本供后续判断使用
- 模型一次返回多个工具调用时，按安全性分批执行：只读工具并发跑，有副作用的工具串行跑
- 提供 /plan、/do 两段式指令，让用户可以先让模型在只读工具限制下产出计划，确认后再切换到全工具模式执行

## 功能需求

- F1：Agent Loop 反复执行"发起 LLM 请求 → 识别工具调用 → 执行工具 → 结果写回历史"，直到模型某一轮回复不再包含工具调用请求，即视为任务完成，循环正常结束
- F2：系统提供固定的最大迭代轮次上限（默认 20 轮，1 轮 = 1 次 LLM 请求 + 其触发的工具执行），达到上限时终止循环，向用户明确提示"已达到最大迭代轮数"，不再发起新的请求
- F3：用户可以在循环执行期间通过按键（Esc 或 Ctrl+C）中断当前 Loop：当前正在执行的这一步（LLM 请求或工具调用）执行完后，循环停止后续迭代，回到空闲输入态，不退出整个程序
- F4：模型连续两次请求调用注册中心中不存在的工具名时，终止本轮循环并向用户说明原因；每次未知工具调用都先把清晰错误写回对话历史，给模型一次基于反馈纠正的机会，只有连续两次都失败才终止
- F5：循环中任意一轮的 LLM 请求发生流式错误（网络、鉴权等）时，立即终止本轮循环，向用户展示清晰错误信息，不崩溃程序，且不影响下一轮正常对话
- F6：系统提供一套异步事件流，把 Agent 循环内部产生的事件（文本增量、工具调用开始、工具调用结果、Token 用量、循环进度、终止原因）与终端展示解耦；界面只订阅事件流即可完成渲染，不直接感知 Agent 内部状态
- F7：系统对每一次 LLM 流式响应做双路收集：一边把文本增量实时转发到事件流供界面展示，一边在内部累积出这一轮的完整文本，供后续判断（是否有工具调用、写入历史）使用
- F8：模型一次返回多个工具调用时，系统按工具的安全性分类分批执行：只读、无副作用的工具（读文件/按模式找文件/搜代码内容）可以并发执行；有副作用的工具（写文件/改文件/执行命令）必须串行执行，且安全批次与有副作用批次之间不交叉并发
- F9：每次 LLM 请求得到响应后，系统产出该次请求的 Token 用量事件（输入/输出 token 数），供界面展示循环进度和成本参考
- F10：系统提供 /plan 和 /do 两个交互指令：输入 /plan 进入计划模式，之后的每一轮对话都只把只读工具集暴露给模型，直到用户输入 /do 切回全工具模式；计划模式下模型仍可正常输出文字讨论、给出计划，只是拿不到有副作用的工具
- F11：循环的五种终止路径（正常结束、达到迭代上限、用户取消、连续未知工具、流式错误）都必须通过事件流清晰地告知界面对应的终止原因，界面据此向用户展示明确提示，不能让用户误以为程序卡住或崩溃

## 非功能需求

- N1：引入 asyncio 后，02-tools 已验收的行为（工具调用、路径安全边界、超时保护、错误兜底、不带工具调用的普通聊天）必须保持等价，不能因为异步化引入新的竞态条件或行为差异
- N2：execute_command 的子进程执行改为异步方式（如 asyncio.create_subprocess_shell），保证超时、取消都不会阻塞事件循环，也不留下僵尸进程
- N3：安全工具批次并发执行时，其中一个工具失败或抛出未预期异常，不能影响同批次其他工具的结果收集，每个工具的结果相互独立、互不干扰
- N4：迭代上限（20 轮）、未知工具容忍次数（连续 2 次）等阈值要有明确的默认值，并集中定义在一处，不散落在多个模块里
- N5：agent 模块只产出异步事件，不直接持有或调用终端渲染对象（Console 等）；异步化之后这条"agent 与 tui 解耦"的原则要在跨 async 边界的情况下继续成立
- N6：Plan Mode 的只读限制通过"这一轮请求携带的工具列表"来实现，不依赖模型自觉遵守文字约定——即使模型在计划模式下"想"调用写文件工具，系统也因为该工具未出现在可用工具列表中而使其在协议层面不可能被调用

## 不做的事

- 不做工具执行前的用户确认 / 权限弹窗系统——延续 02-tools"全部自动执行"的设定；Plan Mode 的只读限制只是简单切换可用工具集合，不是权限系统
- 不做上下文压缩 / 历史裁剪——长对话导致历史膨胀、接近 token 上限的问题留给后续章节
- 不做用户交互式的单次工具调用确认（如"是否允许执行这条命令"的弹窗）——留给后续章节的权限系统
- 不做工具调用 / 循环状态的磁盘持久化或断点续跑——延续"纯内存对话历史"的设定，进程重启后循环状态不保留
- 不做六个核心工具之外的新工具——沿用 02-tools 的 read_file / write_file / edit_file / execute_command / glob_files / grep_content
- 不做多用户 / 多会话并发——单进程单会话模型不变
- 不做迭代上限、未知工具容忍次数等阈值的运行时可配置化（如命令行参数、配置文件项）——先用代码里的固定默认值，需要时后续章节再开放配置

## 验收标准

- AC1：给模型一个需要多步操作才能完成的任务（如"读取 A 文件，根据内容创建 B 文件，再执行命令验证结果"），无需用户在中途催促，Agent Loop 自动连续执行多轮"请求 → 工具 → 结果"，直到给出最终文字回复
- AC2：人为构造一个需要超过默认上限（20 轮）才能完成的循环场景，验证第 20 轮结束后循环终止，界面明确提示"已达到最大迭代轮数"，不再继续请求
- AC3：在 Agent Loop 执行期间按 Esc 或 Ctrl+C，验证当前正在执行的步骤跑完后循环立即停止、回到空闲输入提示符，整个程序未退出，可以继续下一轮正常输入
- AC4：构造模型连续两次请求不存在的工具名的场景，验证第一次未知工具调用后模型收到错误反馈并重试，第二次仍未知时循环终止并提示原因；另构造"只出现一次未知工具、随后模型改为调用已知工具"的场景，验证循环不会被提前终止
- AC5：在循环某一轮的 LLM 请求过程中人为制造流式错误（如断网 / 无效凭证），验证循环立即终止、界面展示清晰错误信息、程序不崩溃且可以继续下一轮正常输入
- AC6：构造一次模型同时返回多个只读工具调用（如同时 glob_files + grep_content）的场景，验证多个工具确实并发执行（可通过总耗时接近单个工具耗时而非各工具耗时总和来验证）
- AC7：构造一次模型同时返回多个工具调用、且其中至少一个是有副作用工具（如 write_file）的场景，验证有副作用的工具按顺序串行执行，不与其他工具并发
- AC8：每一轮 LLM 请求结束后，界面上能看到本轮的 Token 用量信息
- AC9：输入 /plan 后要求模型执行一次写文件操作，验证模型这一轮只能拿到只读工具（无法真正写文件，因为写工具未出现在可用工具列表里），模型只能给出计划性文字回复；随后输入 /do，再次提出同样的写文件请求，验证这次能正常执行
- AC10：在 /plan 模式下连续进行多轮对话（不输入 /do），验证每一轮都保持只读工具限制，不会在中途自动恢复全工具模式
- AC11：把 protocol 从 anthropic 切换为 openai（或反之），以上 Agent Loop 相关场景在两种协议下都正常工作，不改代码只改配置
- AC12：02-tools 已验收的单工具往返场景（如"读一个文件"这种一轮工具调用即可完成的任务）在 Agent Loop 下依然正确工作：模型给出最终回复后，循环在判定"这一轮无新的工具调用"后正常结束，不会多余空转
